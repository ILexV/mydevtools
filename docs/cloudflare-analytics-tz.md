# MyDevTools — анонимная аналитика использования инструментов

> **Техническое задание / TODO для Claude Code**  
> Цель: получить счётчики реального использования инструментов MyDevTools без cookies, fingerprinting, учётных записей и сбора пользовательских данных.  
> Сайт: `https://mydevtools.app` (GitHub Pages за Cloudflare Proxy).  
> Дата подготовки: 2026-10-09.

## 0. Обязательные принципы

- [ ] **Сначала исследуй репозиторий**: фреймворк, маршрутизацию, существующие инструменты, UI, точки выполнения операций, сборку, публикацию GitHub Pages, тесты и текущие Cloudflare-конфигурации. Не предполагай конкретных путей к файлам или наличие Vite/React, пока не проверишь.
- [ ] Сохрани текущий стек и conventions. Не переписывай инструменты ради аналитики. Rust/WASM здесь **не требуется**: передача небольших событий — обычный TypeScript/JavaScript.
- [ ] Сайт, инструменты и пользовательские файлы продолжают работать **полностью в браузере**. Worker нужен только для телеметрии и чтения агрегатов; никакой логики обработки данных на нём.
- [ ] Никаких аналитических SDK третьих сторон, cookies, localStorage/sessionStorage-идентификаторов, browser fingerprinting, клиентских UUID для посетителей, IP или User-Agent в аналитическом dataset.
- [ ] Никогда не передавай введённый текст, файлы, имена файлов, URL анализируемых ресурсов, токены, приватные ключи, содержимое ошибок, параметры операций или пользовательские metadata.
- [ ] Аналитика — **best effort**: её ошибка, таймаут, блокировка браузером или отключение пользователем не влияет на результат инструмента.
- [ ] Считать **операции**, а не уникальных людей. Без идентификаторов посетителей уникальных пользователей и надёжную дедупликацию подсчитать нельзя — не имитировать эти метрики.
- [ ] Не публикуй секреты или account tokens в коде сайта, GitHub Actions logs или публичных API.

## 1. Предлагаемая архитектура

```text
Browser (GitHub Pages)
  └─ tool action -> centralized trackToolEvent(toolId, event)
                         │ POST JSON, no credentials
                         ▼
Cloudflare Proxy -> Worker route /api/analytics/event*
                         │ strict validation / allowlist
                         ▼
              Workers Analytics Engine dataset
                         │
                         └─ private reporting (Cloudflare SQL API
                            or authenticated Worker report endpoint)
```

**Routing:** предпочтительно привязать Worker к точному пути зоны `mydevtools.app/api/analytics/*` через Cloudflare Worker Route, потому что сам основной сайт обслуживается GitHub Pages за включённым Cloudflare Proxy. Для сопутствующего `www` не расширяй маршрут без необходимости; сайт должен использовать canonical origin. Важно: **не привязывай Worker к `mydevtools.app/*`**, чтобы не перехватить весь сайт. Проверить, что маршрут действительно соответствует запросам, а остальные URL по-прежнему идут на GitHub Pages. Не менять существующие DNS A/CNAME-записи, SSL/HTTPS и проксирование.

Допустим альтернативный маршрут на выделенном поддомене (`metrics.mydevtools.app` через Worker Custom Domain) при документированном обосновании, но предпочтителен same-origin `/api/analytics/event`: проще CSP, CORS и работа с блокировщиками. Если выбран поддомен, явно настроить ограничения Origin/CORS; не включать wildcard для произвольных сторонних origin.

### Предлагаемое расположение модулей (адаптировать к реальному репозиторию)

```text
cloudflare/analytics-worker/
  src/index.ts
  src/validation.ts
  src/reporting.ts                 # опционально, только за авторизацией
  tests/*.test.ts

  trackToolEvent.ts               # безопасный, non-blocking клиент

```

Не создавай новую инфраструктуру/монорепо, если в проекте уже есть подходящее место для Worker.

## 2. Контракт событий (MVP)

Endpoint: `POST /api/analytics/event`.

Request JSON:

```json
{
  "tool": "file-hash",
  "event": "tool_completed"
}
```

Обязательные поля и требования:

| Поле | Тип | Ограничение |
|---|---|---|
| `tool` | string | Стабильный `toolId` из утверждённого каталога; не переводимое название, не URL и не произвольный текст |
| `event` | enum | `tool_started`, `tool_completed`, `tool_failed` |

- [ ] На сервере валидировать **точный состав полей** (не принимать дополнительные параметры), Content-Type JSON, размер тела (например, максимум 512 байт), метод POST.
- [ ] Список `toolId` получать из каталога проекта на этапе подготовки к сборке Worker или поддерживать явно синхронизируемый allowlist; не принимать произвольные tool name, в том числе для защиты cardinality.
- [ ] Не отправлять payload с `details`, `error`, `duration`, `filename`, `fileSize`, `pathname`, `referrer`, `sessionId` или `userId` в MVP.
- [ ] При валидном запросе возвращать `204 No Content`; при неверном методе — `405`, неверном payload — `400`, слишком большом теле — `413`.
- [ ] Не добавлять `Set-Cookie`; не читать и не сохранять входящие cookies.
- [ ] Ответы: `Cache-Control: no-store`; запретить кеширование POST на уровне Worker/правил Cloudflare.

### Семантика событий

- **`tool_started`**: реальный запуск обработки по действию пользователя, после локальной валидации входных данных, а не открытие страницы или автоматический пересчёт при наборе текста.
- **`tool_completed`**: после фактического успешного выполнения. Считать даже если операция была очень быстрой. Не отправлять при открытии уже готового результата из истории.
- **`tool_failed`**: операция была запущена, но завершилась ошибкой обработки; не отправлять саму ошибку, stack trace или данные. Ошибки предварительной валидации до начала запуска не считать `failed`.
- Отмена пользователем и ожидаемые abort-сценарии **не считаются ошибками** в MVP; документировать правило. При необходимости отдельно спроектировать `tool_cancelled` в последующем релизе.
- При повторном явном запуске операции считать ещё один запуск. Не добавлять dedup по пользователю/устройству.
- Событие `started` может прийти без `completed` из-за закрытия вкладки, блокировки запросов, abort и т. п. Не обещать точной конверсии.

## 3. Analytics Engine dataset

Dataset: `mydevtools_tool_usage` (или другое явное стабильное имя).

Пример Worker binding в `wrangler.jsonc`:

```jsonc
{
  "name": "mydevtools-analytics",
  "main": "src/index.ts",
  "compatibility_date": "2026-10-09",
  "analytics_engine_datasets": [
    { "binding": "TOOL_ANALYTICS", "dataset": "mydevtools_tool_usage" }
  ],
  "routes": [
    { "pattern": "mydevtools.app/api/analytics/*", "zone_name": "mydevtools.app" }
  ]
}
```

Проверить актуальную схему Wrangler и доступный план Cloudflare перед деплоем. Analytics Engine создаёт dataset при первой записи; ручное создание обычно не нужно.

Пример записи:

```ts
env.TOOL_ANALYTICS.writeDataPoint({
  blobs: [body.tool, body.event],
  doubles: [1],
  indexes: [body.tool],
});
```

**Зафиксировать схему измерений:** `blob1 = toolId`, `blob2 = eventType`, `double1 = 1`, `index1 = toolId`. Время записи берётся из системной метки времени Analytics Engine. Не класть IP, request headers, URL, user identifiers в blobs/indexes. Если важна экономия индексов, выбрать schema и обосновать компромисс до релиза; не менять порядок колонок после запуска без миграционного плана.

- [ ] Протестировать, что событие реально пишется и читается через Analytics Engine.
- [ ] Документировать сохранение событий на **три месяца**; отдельная БД пока не нужна.
- [ ] Не добавлять случайную sampling-логику в MVP: пользователь хочет понятные счётчики операций. При масштабировании лимитов отдельно предусмотреть sampling с честной маркировкой оценок.
- [ ] Задокументировать лимиты тарифов (проверить перед запуском) и мониторинг расхода Workers/Analytics Engine.

## 4. Клиентская интеграция

- [ ] Реализовать единую функцию `trackToolEvent(toolId, event)` без дублирования `fetch` в инструментах.
- [ ] Использовать `fetch('/api/analytics/event', { method: 'POST', headers: {'Content-Type': 'application/json'}, credentials: 'omit', cache: 'no-store', body: JSON.stringify({tool, event}) })` с контролируемым таймаутом/AbortController при необходимости.
- [ ] Вызов не `await`-ить на критическом пути успешной операции; ошибки подавлять без отображения пользователю. Не добавлять автоматический бесконечный retry, offline-очереди, background sync или persistent queue.
- [ ] Если для выгрузки результатов перед закрытием страницы реально нужен `keepalive`, применять точечно, проверить браузерные ограничения и не использовать как обязательное условие.
- [ ] Поддержать опциональный build-time флаг `ANALYTICS_ENABLED` для локального dev/test и выпусков (по умолчанию отключено в тестах); не использовать пользовательские идентификаторы.
- [ ] Нормализовать инструменты с автоматическим результатом по вводу: отправлять только при **явном действии** пользователя (`Run`, `Convert`, `Hash`, `Generate`, `Validate`, и т.д.). Если такого действия нет, не добавлять искусственный автотрекинг каждого изменения.
- [ ] Реальные точки интеграции выбирать после ревизии инструментов. Для каждого инструмента составить матрицу: `toolId`, действие запуска, критерий успеха, критерий ошибки, особые случаи (автоматические вычисления, многошаговые операции).
- [ ] Отправка строго не блокирует WASM/Web Worker/рендер UI и не влияет на обработку файлов.
- [ ] Учитывать режим offline: операция продолжает работать, событие теряется — это ожидаемое поведение.

## 5. Приватность и безопасность

- [ ] Составить privacy data inventory: **сохраняемые поля — только `toolId`, `eventType`, server-side timestamp, count=1**.
- [ ] Никаких client/session IDs, cookie, fingerprint, IP, геолокации, заголовков, рефереров и URL аналитического payload.
- [ ] Не включать логирование raw request body и заголовков для endpoint; проверить настройку Workers Observability, error monitoring и других автоматических логов. Платформа Cloudflare технически обрабатывает сетевые сведения для доставки/защиты запроса, но **приложение не должно сохранять их в своём аналитическом dataset**.
- [ ] Запретить произвольные tool IDs и внезапное расширение схемы клиентом. Не использовать клиентский `Origin`/`Referer` как единственную защиту от злоупотреблений.
- [ ] Добавить разумный edge rate limiting / WAF для endpoint по возможности без сохранения идентификаторов в приложении. Защита от накрутки не абсолютна без идентификации; зафиксировать ограничение в документации.
- [ ] Проверить отсутствие публичного endpoint чтения статистики, SQL execution endpoint и выдачи API tokens.
- [ ] Админские запросы защищать Cloudflare Access (или выполнять только через защищённую консоль/Cloudflare SQL API). Никогда не включать admin/metrics endpoints в публичный бандл сайта.
- [ ] При необходимости добавить короткую заметку пользователям: «Сайт собирает анонимные счётчики выполненных действий с инструментами. Содержимое файлов и введённые данные не отправляются»; убедиться, что формулировка соответствует фактическому поведению сайта.
- [ ] Проверить CSP / Cloudflare security rules и что не требуется сторонних analytics scripts.

## 6. Просмотр результатов и отчёты

**MVP:** достаточно Cloudflare Analytics Engine SQL API / Dashboard и документации с готовыми запросами. Публичную `/admin/analytics` не создавать автоматически. Если интерфейс статистики действительно нужен, реализовать **отдельный защищённый endpoint**, а не публичный API.

- [ ] Подготовить проверенные запросы: топ инструментов за последние 7, 30, 90 дней; started/completed/failed по инструменту; суммарные операции по дням; ошибки по инструментам.
- [ ] Учитывать, что три месяца — верхняя граница истории; выбирать начальную временную границу в SQL и проверять поддерживаемый синтаксис API.
- [ ] Если создаётся reporting Worker, рассмотреть **Analytics SQL binding** (`[analytics] binding = "ANALYTICS_SQL"`, Wrangler >= 4.145.0) для запросов без API token; SQL выполнять только из доверенного кода с фиксированными/параметризованными запросами.
- [ ] Не принимать пользовательский произвольный SQL от браузера.
- [ ] Для долгосрочного хранения за пределами трёх месяцев отдельной следующей задачей описать дневные агрегаты в Cloudflare D1 с контрольной процедурой агрегации и идемпотентным UPSERT; **не включать D1 в MVP**.

Примеры отчётов должны использовать реальные имена таблиц/колонок, уточнённые через документацию/тестовый SQL, а не выдавать псевдозапросы как гарантированно рабочие.

## 8. Критерии приёмки (Definition of Done)

- [ ] При открытии страницы или вводе текста **нет** event request.
- [ ] Одно явное успешное действие: `tool_started` и `tool_completed` (каждое по одному разу).
- [ ] Ошибочная операция после начала: `tool_started` и `tool_failed`; нет `tool_completed`.
- [ ] Непрошедшая локальная валидация: нет событий.
- [ ] При 500/429/timeout/offline аналитики пользователь всё равно получает корректный результат обработки.
- [ ] Содержимое файла, поля формы, ключи/токены, имена файлов и stack traces не попадают в payload, dataset или лог приложения.
- [ ] Внешняя запись с неизвестным `toolId` или `event` отклоняется.
- [ ] GET /api/analytics/event, лишние поля, не-JSON или большое тело отклоняются.
- [ ] Данные доступны в Analytics Engine; проверенный запрос показывает выбранный инструмент и корректное число тестовых событий.
- [ ] Нет открытого API для чтения приватной статистики и секретов в фронтенде.
- [ ] GitHub Pages работает по прежним URL, Cloudflare Proxy/Analytics и HTTPS не нарушены.
- [ ] Worker развёрнут только на analytics route; запросы к остальным URL сайта не перехватываются.
- [ ] Все тесты, сборка и линтер проекта проходят; проверить browser smoke на реальном UI и кратко отчитаться о результатах.
- [ ] Деплой задокументирован и воспроизводим, rollback — отключить Worker route / feature flag без изменения работоспособности сайта.

## 9. Отложенные задачи — не блокируют MVP

- [ ] Дневные агрегаты в D1 для истории за год и более.
- [ ] Новое событие `tool_cancelled`, если появится реальная потребность.
- [ ] Детализация по версиям инструментов только после оценки приватности и cardinality.
- [ ] Автоматизированные отчёты по неделям / месяцам.
