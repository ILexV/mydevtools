# MyDevTools — TODO / Roadmap

> **Концепция:** сложная обработка данных, простой интерфейс, всё локально в браузере. Сайт статический (GitHub Pages + Cloudflare), без backend. Rust/WebAssembly используется там, где он даёт преимущество при обработке больших объёмов данных, потоковых вычислениях или переиспользовании зрелых библиотек. Простые операции могут оставаться на JavaScript / Web APIs.

> **Исключение для сетевых утилит (§5):** опциональный Windows-агент выполняет запросы к выбранным пользователем адресам вне браузерной песочницы. Токен сопряжённой сессии хранится в браузере. Рабочие запросы HTTP-клиента хранит в зашифрованном виде агент на компьютере пользователя (§5.2.1); в браузере они остаются только до первого подключения агента с хранилищем. Это исключение из общего правила хранения ниже.

## Принципы и общие требования

- [x] Все файлы и чувствительные данные обрабатываются локально, без отправки на сервер.
- [x] Для каждого инструмента есть простой самостоятельный интерфейс: выбор файла/ввод → настройки → результат/экспорт (без обязательных визуальных pipeline).
- [x] Разграничить задачи JavaScript/Web APIs и Rust/WASM; не переносить простые операции в WASM без причины.
- [x] Предусмотреть поддержку больших файлов без обязательной полной загрузки в память.
- [x] Тяжёлые вычисления выполнять вне UI-потока (Web Workers).
- [ ] Отображать прогресс, количество обработанных байтов, прошедшее время, скорость и состояние задачи.
- [ ] Поддержать отмену длительных операций и корректное освобождение ресурсов.
- [x] WASM-модули загружать по требованию; не включать все библиотеки в стартовый bundle.
- [ ] Обработать ограничения памяти браузера, квоты хранилища и нехватку ресурсов понятными сообщениями.
- [x] Проверить работу при отключённом интернете после загрузки нужных модулей (PWA/offline caching).
- [x] Не сохранять секреты/ключи/содержимое файлов в localStorage по умолчанию.
- [ ] Добавить тесты корректности и производительности на файлах разных размеров.

### 1.2 Binary File Analyzer / Hex Viewer (P1)

- [x] Просмотр крупных файлов в hex + ASCII/UTF-8, виртуализация отображаемых строк.
- [x] Переход к смещению, поиск сигнатур и последовательностей байтов.
- [x] Определение вероятного формата по magic bytes.
- [x] Отображение размера, смещений, заголовков и базовой энтропии по блокам.
- [x] Экспорт выбранного диапазона без копирования всего файла в память.

Реализован `hex-viewer` на всех 10 языках (2026-10-14): локальный файл, виртуальные строки по 16 байт (hex, ASCII и UTF-8), переход по десятичному или `0x` смещению, сигнатура по тем же magic bytes, что и у base64, поиск текста или hex и энтропия Шеннона по блокам 4 КиБ. Поиск и энтропия идут в worker с прогрессом и отменой; видимые строки читаются через `File.slice`. Экспорт — включительный диапазон как срез Blob, без второй копии всего файла. Пределы: образец 256 байт, 200 совпадений, чтение поиска по 1 МиБ, энтропия целиком до 1 МиБ и далее не больше 256 проб, экспорт 256 МиБ. Правка байтов и дизассемблирование не входят. В браузере на разреженном файле 2 ГиБ проверены переход к последнему байту, останов поиска `00` на 200 совпадениях и 256 проб энтропии. Полный проход по плотному многогигабайтному файлу без раннего совпадения не засекался.

### 1.3 Large File Diff (P1)

- [x] Сравнение больших текстовых файлов с ограниченным потреблением памяти.
- [x] Сравнение бинарных файлов по блокам, список отличающихся диапазонов.
- [x] Настройки для текстового сравнения: переводы строк, пробелы, кодировка.
- [x] Экспорт отчёта о различиях.

Реализован `large-file-diff` на всех 10 языках (2026-10-23):
- **Память.** Каждая строка хранится как 64-битный хэш плюс одно смещение на 256 строк — около 8 байт на строку и до 9 байт сверху на время сопоставления. Предел — 10 млн строк на файл. Текст строк на экране и в отчёте дочитывается из файлов.
- **Алгоритм.** Общие начало и конец отбрасываются, затем ставятся якоря на строки, уникальные в обоих файлах (patience), а промежутки выравниваются линейным по памяти алгоритмом Майерса с лимитом работы. Промежуток сверх лимита показывается как замена, и страница об этом говорит. На случайных входах результат минимален: проверено сверкой с LCS в тестах.
- **Настройки.** Пробелы: точно, конец строки, количество, все. CRLF/LF вместе с отсутствующим последним переводом строки можно не учитывать. Кодировка: авто по BOM, UTF-8, UTF-16 LE/BE и 7 устаревших. UTF-8 и UTF-16 хэшируются по кодовым точкам, поэтому один и тот же текст в разных кодировках совпадает.
- **Бинарный режим.** Сравнение блоками по 1 МиБ, словами по 4 байта; диапазоны отличий с первыми 16 байтами каждой стороны, хвост более длинного файла — последний диапазон. Хранится 100 000 диапазонов, остальные только считаются.
- **Отчёт.** Unified diff (.diff, применяется GNU patch побайтно в строгом режиме) или CSV диапазонов, потоком в выбранный файл.
- **Замеры в Chromium:** 2 × 168 MB (2 млн строк) — 6,5 с; 2 × 531 MB (6 млн строк) — 18 с. В Firefox и WebKit те же результаты (8,0 с и 5,9 с на 2 × 168 MB).

### 1.4 Compression Tools / Benchmark (P1)

- [x] Сжатие и распаковка ZIP, TAR/GZIP, а также сравнение Zstd/Brotli/Gzip там, где это реализуемо в браузере.
- [x] Настройка уровня сжатия и отображение коэффициента сжатия.
- [x] Измерение времени, скорости и потребления памяти.
- [x] Просмотр содержимого архива, извлечение выбранных файлов.
- [x] Защита от path traversal и небезопасных имён файлов при извлечении.
- [x] Ограничения против архивных бомб и чрезмерного расхода памяти.

Реализованы `archive-explorer` и `compression-benchmark` на всех 10 языках (2026-10-23) поверх нового WASM-домена `compression` (flate2/miniz_oxide, brotli, zstd; 1,8 МБ, 0,7 МБ в gzip):
- **Кодеки.** Потоковые кодеры gzip/deflate/zlib/Brotli/Zstandard с CRC-32 и декодер с выдачей не больше заданного окна за вызов: бомба никогда не раздувается в памяти больше чем на 1 МиБ. Склеенные члены gzip и кадры zstd, нулевой хвост tar.gz, проверка CRC и ISIZE gzip. Окно Zstandard ≤128 МиБ, Brotli строго по RFC 7932.
- **Чтение архивов.** ZIP по центральному каталогу (ZIP64, SFX-заглушка, имена Info-ZIP Unicode, CP437); TAR (ustar, длинные имена GNU, pax, размеры base-256) с произвольным доступом; TAR и одиночные файлы внутри gzip/zstd/Brotli — одним потоковым проходом. Таблица, фильтр, выбор строк/папок/найденного.
- **Извлечение.** Один файл, ZIP выбранного или (Chromium) прямо в выбранную папку без перезаписи существующих файлов. Абсолютные пути, буквы дисков, `..`, управляющие символы, слишком длинные имена не пишутся; запрещённые Windows символы и имена устройств заменяются; ссылки не создаются. Перекрывающиеся записи ZIP отклоняются; размер и CRC-32 каждой записи сверяются; рост больше 1000× после 64 МиБ и вывод больше 64 ГиБ останавливают извлечение; до 1 млн записей и каталог до 256 МиБ.
- **Создание.** ZIP (Deflate 0–9, имена UTF-8, ZIP64 от 4 ГиБ), TAR, TAR.GZ, TAR.ZST потоком в сохраняемый файл; проверено `unzip -t`, GNU tar и побайтной сверкой.
- **Бенчмарк.** Первые 1–256 МиБ файла; каждый кодек и уровень в свежем worker, поэтому рост heap WASM относится только к нему (отдельно для сжатия и распаковки); время только вызовов кодека; проверка распаковкой (длина + CRC-32); встроенный gzip CompressionStream для сравнения; CSV; любая строка сжимает весь файл в .gz/.br/.zst.
- **Проверено** в Chromium, Firefox и WebKit: tar.gz/tar.zst/tar на 168 МБ и a.log.gz извлекаются побайтно точно (Chromium 3,4–3,5 с), извлечение в папку (OPFS в тесте) переименовывает повторы в « (2)», бомба 1 ГиБ нулей останавливается с понятной ошибкой, bzip2 отклоняется по имени. Бенчмарк на 16 МиБ лога: 11 прогонов за 36 с в Chromium, 45 с в WebKit, 195 с в Firefox (там медленнее Zstandard 19); сохранённые .gz/.zst/.br распаковываются `gzip`/`zstd`/декодером обратно в исходный файл. 375 и 1440 px без горизонтальной прокрутки, обе темы, 10 языков, консоль чистая.
- **Ограничения.** Методы ZIP: Stored, Deflate, Zstandard; шифрование, BZIP2, LZMA, Deflate64 только показываются. Без диалога сохранения (Firefox, Safari) скачивание ≤512 МиБ; извлечение в папку только там, где есть `showDirectoryPicker`. Размер одиночного сжатого файла известен только после извлечения.

При сверке 2026-10-17 смешанные пункты разделены: сортировка, группировка/агрегаты, преобразование типов и Parquet остаются открытыми именно в CSV Explorer; соответствующие сценарии доступны в новых SQL Playground и конвертере. Пределы: поле 2 MiB, запись 8 MiB, 512 колонок, 100 млн записей; экспорт потоковый, Blob-fallback — 512 MiB.

**Типы, сортировка, группировка и Parquet — 2026-10-22.** Столбцам задаётся тип: текст, целое int64 (BigInt, точно), число double или логическое значение. Тип выбирается вручную или определяется по первым 1000 строкам; значения с ведущими нулями остаются текстом. Неверное значение по выбору останавливает задачу с указанием столбца и строки данных или становится null. Таблица всегда показывает исходный текст; типы действуют на сортировку, группировку и экспорт. Сортировка отфильтрованного результата идёт по одному столбцу: ключи и диапазоны записей держатся в typed arrays, до 5 млн строк и 32 млн символов текстовых ключей. Пустые значения идут последними, текст сравнивается по кодам символов, сортировка стабильна. Отсортированные строки читаются окнами (до 65 536 строк / 32 MiB): позиции упорядочиваются по смещению, близкие диапазоны склеиваются в крупные чтения. Группировка — по одному столбцу или по всему результату: количество строк, для столбца итогов — число непустых, точная сумма (BigInt для целых, компенсированное суммирование для double), среднее, минимум и максимум; до 100 000 групп. Изменение фильтра или типов сбрасывает итоги, активная сортировка пересобирается. Экспорт строк или итогов — в CSV (нормализованные значения типизированных столбцов, защита от формул только для текста), JSONL (настоящие числа/логические/null; int64 без потери цифр) и Parquet (потоково через `hyparquet-writer`, Snappy, группы строк до 65 536 строк, столбцы STRING/INT64/DOUBLE/BOOLEAN, nullable). Сумма целых вне int64 в Parquet не пишется — показывается ошибка с советом выгрузить CSV/JSONL. **Проверено 2026-10-22**: модульные тесты преобразований, определения типов, агрегатов и потокового Parquet с обратным чтением через hyparquet. В браузере на собранном сайте: 200 000 строк — определение типов, сортировка по числу (~2 с) и тексту, хвост с пустыми значениями, экспорт отсортированных строк в JSONL/Parquet (~5 с; Parquet прочитан обратно, int64 точные), группы с экспортом в Parquet/CSV, фильтр с автоматической пересортировкой, ошибка преобразования и политика null, переполнение суммы для Parquet, 500 групп с прокруткой и отказ на 200 000 группах, отмена сортировки. Файл 5 000 001 строка: отказ сортировки по пределу без потери сессии, после фильтра сортировка 5 000 000 строк ~27 с, группировка ~20 с. Обе темы, 375 px, все 10 языков. Не проверено: файлы в гигабайты с сортировкой и браузеры кроме Chromium.

Реализован `parquet-explorer` на всех 10 языках (2026-10-14): локальный `.parquet`, схема, метаданные, статистика row groups, виртуализированный просмотр выбранных колонок и экспорт этих колонок в CSV/JSONL. Тесты покрывают STRING, INT64 с сохранением десятичного написания (включая значения больше 2^53), BOOLEAN, DOUBLE, TIMESTAMP и BYTE_ARRAY. В браузере также зарегистрированы Zstd, LZ4 и LZ4_RAW; LZO не поддерживается. Пределы: 512 колонок, ячейка 1 MiB; с 2026-10-17 экспорт CSV/JSONL потоковый, Blob-fallback — 512 MiB. SQL, фильтры, агрегаты, сортировка и запись Parquet не добавлены в этот обозреватель: для них есть отдельные новые инструменты. Крупные файлы этим срезом не проверялись.

Фильтры, агрегаты и проверка крупных файлов (2026-10-23):
- До 8 условий через И по любой колонке. Числа сравниваются точно: INT64 как BigInt, DOUBLE и DECIMAL как десятичная запись. Время сравнивается по моменту, логические значения как true/false, текст с учётом регистра или без. Пустое значение подходит только под «пусто».
- Результат фильтра — битовая маска плюс счётчики на каждые 4096 строк, по одному биту на строку. Таблица, инспектор, группировка и экспорт работают с подходящими строками; окна без совпадений не читаются.
- Группировка по одной колонке (или итог по всему результату): счётчик, а для колонки итогов — непустые, точная сумма, среднее, минимум и максимум. Не больше 100 000 групп. Итоги можно скачать в CSV или JSONL.
- Скан идёт по группам строк. Если у колонок есть offset index, файл читается окнами по 65 536 строк, иначе каждая группа распаковывается один раз. Таблица в группах без offset index читает группу целиком и берёт её из кэша; раньше прокрутка такой группы была квадратичной.
- Короткие ASCII-строки декодируются без TextDecoder: это ускоряет текстовые фильтры в Chromium примерно в 2,4 раза.
- Отмена фильтра, группировки или экспорта заново открывает файл (это чтение одного футера), а не закрывает его.
- Замеры в Chromium на 20 000 000 строках (395 MB, 20 групп строк, Snappy, с offset index): открытие 2 с; фильтр «содержит» по текстовой колонке 41 с; группировка по категории с суммой 18,5 с; прокрутка в конец отфильтрованного результата мгновенная.
- Файл на 5 000 000 строк без offset index (99 MB): числовой фильтр 2,2 с, переход в середину таблицы — одно чтение группы.
- В Node: экспорт отфильтрованных строк из 20M — 18 с, RSS около 1,2 GB.
- Сортировка, SQL и запись Parquet остаются в CSV Explorer и Local Data Playground.

## Этап 4 — Рабочий стол (по образцу Nomos Desktop Shell)

Чеклист собран по коду `/home/lex/github/nomos` (ветка `feat/desktop-shell`, коммиты `bb1a266`…`9df73af`, целиком лежит в `main`; после слияния на `main` ещё `17f73db`…`7e77b4d`). Опора в Nomos: `docs/desktop/architecture.md`, `docs/desktop/backlog.md`, ADR 0020–0024, `frontend/src/desktop/`.
>
> **Задача здесь:** страницы `/{lang}/{slug}/` остаются индексируемыми адресами. Рабочий стол — отдельный режим для большого монитора: ярлыки, несколько окон, в каждом текущая страница инструмента без SEO-обвязки. Внешний вид — Prism (`--mdt-*`, `ds-*`), поведение — из Nomos. Код Nomos на React не копируется: переносятся сценарии и чистые функции геометрии.

**Готово, когда:** с главной можно открыть стол, поставить несколько инструментов рядом, свернуть и восстановить их после F5, а прямой заход на `/{lang}/{slug}/` по-прежнему отдаёт полную страницу с тем же canonical.

### Чем стол MyDevTools отличается от Nomos

- Окно — отдельный документ: `iframe` на `/{lang}/{slug}/?embed=1`. Контроллеры ищут один корень на документ (`document.querySelector("[data-…-tool]")`) и второй экземпляр в той же странице не оживает. Фрейм это обходит и позволяет две копии одного инструмента.
- Адресная строка стола остаётся `/{lang}/desktop/`. В Nomos адрес зеркалит активное окно (ADR 0021); здесь тот же приём подменил бы каноническую страницу инструмента. Полная страница открывается командой окна «Открыть на всю страницу».
- Настройки стола живут в браузере. В Nomos обои и ярлыки уехали на `GET/PUT /api/v1/desktop-preferences` с ревизией. Сервера у сайта нет.
- Каталог строится из `apps/site/src/registry/tools.ts` и категорий, не из меню с ролями.
- Свёрнутое окно остаётся смонтированным (урок Nomos: свёртка не сбрасывает ввод). Закрытие уничтожает фрейм. Десяток тяжёлых обозревателей держать открытыми не цель.

### Вне объёма

- Серверные настройки, ревизия, HTTP 409, таблица `desktop_preferences`, перенос localStorage на сервер.
- Виджеты кадрового контура: «Мой день», отсутствия, сроки документов, вакансии, табель, лента, сводка рисков, опрос раз в 10 минут.
- Сохранённые виды фильтров реестров и рабочие наборы с адресами карточек сотрудников.
- Роли, юрлицо, филиал, сессия, смена пароля, профиль как окно.
- `react-rnd` и CSS `transform` на кадре. В Nomos кадр стоит на `left`/`top`, потому что меню внутри трансформированного предка обрезается. У инструментов меню и выпадающие списки тоже живут внутри страницы.
- Автоматический увод главной на стол. Поисковик и первый визит видят каталог.

### 5.2.1 Зашифрованное хранилище у агента

> **Решение владельца 2026-10-21.** Рабочие данные HTTP-клиента переезжают из `localStorage` в зашифрованное хранилище на компьютере пользователя через агента. Ключ защищает Windows DPAPI, пароль при запуске не нужен. Переносится всё рабочее пространство, не только секреты. Хранилище делается раньше окружений и Auth: секреты сразу живут в нём, без второго переезда. После этого исключение для HTTP-клиента в шапке файла меняется: в браузере остаются только токен сессии и настройки вида.

**Модель угроз.** Файлы на диске зашифрованы: кража диска, другой пользователь Windows, очистка данных сайта и смена браузера их не раскрывают. От XSS на `mydevtools.app` хранилище данных само по себе не защищает: токен сессии лежит в браузере, и вредный скрипт попросит агента так же, как страница. Поэтому секреты устроены иначе: страница их только записывает, значение подставляет агент, и только для разрешённых хостов.

Агент:
- [x] Ключ данных — 32 случайных байта. На Windows он хранится обёрнутым DPAPI (`CryptProtectData`, область текущего пользователя). Сборка не для Windows хранит ключ файлом с правами `0600`; это режим разработки, не шифрование в покое.
- [x] Каждый файл зашифрован AES-256-GCM (`ring`, уже в зависимостях через rustls) со случайным nonce. Associated data — origin, вид записи и имя: файл нельзя подменить другим.
- [x] Каталог по умолчанию `%APPDATA%\MyDevTools\Agent\vault`, флаг `--data-dir` для разработки и тестов. Данные разных origin лежат раздельно: dev-сервер не видит данные `https://mydevtools.app`.
- [x] Ключа нет, а зашифрованные файлы есть — агент сообщает `vault_key_unavailable` и не создаёт новый ключ поверх старых данных.
- [x] Атомарная запись: временный файл, `fsync`, rename. Лимиты на размер документа и их число.
- [x] Документы с ревизией. Запись с устаревшей ревизией получает `revision_conflict` и текущую ревизию, а не затирает чужое сохранение.
- [x] Capability `vault.data`: чтение, запись и удаление документов (рабочее пространство, окружения, история).
- [x] Capability `vault.secrets`: список имён и хостов без значений, запись и удаление секрета. Значение секрета наружу не отдаётся никаким маршрутом.
- [x] Подстановка в `http.request`: `{{secret:имя}}` в URL, значениях заголовков и теле. Секрет подставляется, только если хост запроса входит в его список (`api.example.com` или `*.example.com`). Неизвестное имя — `secret_not_found`, чужой хост — `secret_host_denied`. Подстановке нужны и `http.request`, и `vault.secrets`.
- [x] Редирект запроса с секретом на хост вне списка не выполняется: страница получает сам ответ 3xx.
- [x] Значение секрета, вернувшееся в ответе (эхо заголовков, тело, итоговый URL), заменяется на `{{secret:имя}}`. Это защита от простого эха, не от преобразованного значения.
- [x] Экспорт и импорт хранилища файлом под паролем (Argon2id) для переноса на другой компьютер: DPAPI на другую машину не переносится. Сделано 2026-10-22. Запускается только кнопками «Экспорт хранилища…» и «Импорт хранилища…» в окне агента: у страницы нет маршрута, поэтому пароль и файл в браузер не попадают, и секреты остаются «только на запись». Файл `.mdtvx` — все сайты (документы, секреты, клиентские сертификаты с ключами) в одном JSON, запечатанном AES-256-GCM ключом из Argon2id (64 MiB, 3 прохода, 1 поток, соль 16 байт; параметры и соль — associated data). Пароль на экспорт не короче 8 символов, повтор обязателен. Импорт сначала проверяет всё содержимое теми же правилами, что и маршруты (имена, значения секретов, хосты, совпадение ключа с сертификатом, размеры), потом пределы хранилища; при превышении не пишется ничего. Записи с тем же именем заменяются, документ продолжает свою ревизию, остальное остаётся. Чтобы экспорт знал адрес сайта, в каталоге сайта теперь лежит запечатанная метка `origin.mdtv`; она появляется при первом обращении сайта к хранилищу после обновления, а сайты без метки экспорт пропускает и называет их число. Чужой файл, неверный пароль и завышенная в заголовке стоимость Argon2 (больше 256 MiB, 10 проходов, 4 потоков) отклоняются до записи.

### 5.2.2 До уровня Postman

Порядок по пользе. Mock-серверы, мониторы и командная синхронизация в объём не входят: у сайта нет backend.

Фаза 1 — фронтенд поверх хранилища §5.2.1:
- [x] Окружения и переменные: `{{var}}` в URL, параметрах, заголовках, теле и полях Auth; приоритет «окружение → папки от ближней к корню (переменные коллекции) → глобальные»; значения могут ссылаться на другие переменные, цикл остаётся как написан; встроенные `{{$guid}}`, `{{$timestamp}}`, `{{$isoTimestamp}}`, `{{$randomInt}}`. Переключатель окружения в шапке запроса, окно «Окружения» (глобальные, создать, переименовать, дублировать, удалить), переменные папки в окне «Настройки папки». Незаданные переменные перечисляются над вкладками и уходят как написаны. Секретная переменная — значение `{{secret:имя}}`. Таблица параметров больше не кодирует `{{…}}` в `%7B%7B`.
- [x] Вкладка Auth с наследованием от папки: Наследовать, None, Basic, Bearer, API Key (заголовок или query), OAuth 2.0 client credentials (токен через агента, только в памяти страницы, кнопка «Получить новый токен», автозапрос при отправке, обновление за 30 с до истечения), AWS SigV4 (подпись в браузере через WebCrypto, сверено с векторами AWS `get-vanilla`, `get-vanilla-query-order-key-case`, `post-x-www-form-urlencoded`). Auth заменяет одноимённый заголовок. Basic с `{{secret:…}}` кодирует агент: новое поле `basicAuth` в `/v1/http/request`, эхо закодированной пары маскируется в Base64 шаблона. Для SigV4 `{{secret:…}}` запрещён: подпись считает страница. **Проверено 2026-10-21** в браузере против отладочного агента и локального эхо-сервера с token endpoint: Bearer из окружения, глобальная переменная, API key в query из секрета, SigV4, отказ SigV4 с секретом, OAuth с client secret из хранилища через Basic агента, наследование Basic с секретом от папки (цель получила настоящий пароль, страница — шаблон), правка переменной папки, сохранение после перезагрузки; консоль чистая, обе темы, 375 px.
- [x] Типы тела: выбор «Без тела», Raw (текст, JSON, HTML, XML как раньше), form-data, x-www-form-urlencoded, двоичный файл, GraphQL (query и variables). Старые запросы без режима открываются как Raw, новый запрос — «Без тела». form-data: строка — текст или файл, `multipart/form-data` с границей собирает страница и заменяет заданный вручную Content-Type. urlencoded кодирует ключи и значения, `{{…}}` остаются как есть. GraphQL уходит JSON `{query, variables}`, переменные — только JSON-объект. Файлы хранятся только в памяти страницы, в рабочей области — имя, размер и тип; после перезагрузки строка помечена «выберите заново», отправка сообщает, какой файл выбрать. - [x] Импорт cURL в запрос и генерация кода: cURL, fetch, Python requests, HTTPie. Импорт — пункт «Импорт cURL…» в меню дерева (новый запрос в папке) или вставка команды в поле URL (заменяет поля открытого запроса, имя и Auth без `-u` остаются). HTTPie на машине не установлен, его сниппет проверен только тестом.
- [x] Импорт и экспорт Postman Collection v2.1. В меню дерева: «Импорт из Postman…» (файл JSON; коллекция становится папкой в выбранном месте, её auth и variables — настройками этой папки) и «Экспорт в Postman…» для папки и для корня (клик по пустому месту списка). Доступ к частной сети — переключатель «Разрешить локальную сеть и этот ПК как цель» в окне агента: по умолчанию выключен, запоминается в `HKCU\Software\MyDevTools\LocalAgent` (`AllowPrivateNetwork`), действует на все инструменты и читается при каждой проверке цели, так что выключение останавливает идущее сканирование частной цели. `--allow-private` включает его на запуск, и галочку тогда не снять. Каждый сканер — своя capability (`port.scan`, `network.scan`); страница сканера просит только своё право, другие страницы сканеры не запрашивают. В процессе агента не больше двух сканирований сразу. «Остановить» идёт через `/v1/http/cancel`, который теперь принимает любую сопряжённую сессию и достаёт только её операции; отзыв сессии и выход агента тоже останавливают скан.
- [x] Сканирование портов `port-scanner`: один хост, до 65535 портов. Connect-скан без данных и баннеров: open, closed (отказ), filtered (таймаут), unreachable, собственный порт агента — denied без соединения. До 64 соединений сразу, таймаут 200–5000 мс, до 1024 диапазонов; при скане больше 1024 портов в ответ идут только открытые, остальное — счётчики. Поток NDJSON, прогресс раз в 250 мс. Наборы: 70 популярных портов, 1–1024, все, свой список. Хранится набор, свой список, таймаут и параллельность (`mdt.port-scanner.v1`); хост и результаты — нет.
- [x] Сканирование сети `network-scanner`: только свои подсети. IPv4 CIDR от /22 до /32, который лежит внутри сети одного из интерфейсов компьютера (`network_not_local`, шире /22 — `network_too_large`); список сетей — `GET /v1/scan/networks` (link-local выкинут, сеть шире /22 сужена до /22 вокруг адреса). Адрес сети и широковещательный пропускаются до /30. 32 адреса сразу: ICMP echo, TCP на до 16 портов проверки (отказ тоже значит «жив»), ARP (Windows `SendARP`, Linux `/proc/net/arp`), по желанию обратный DNS; свой адрес помечен «этот ПК». Хранятся порты проверки, таймаут и поиск имён (`mdt.network-scanner.v1`); сеть и хосты — нет.

### 5.4 Трассировка пути (MTR)

Ориентир — WinMTR 0.92, https://github.com/WinMTR/WinMTR-Official. Лицензия GPL-2.0: повторяем поведение, исходники не копируем. Браузер ICMP не отправляет. Это новая capability агента, например `icmp.trace`. Право `http.request` она не наследует. Публичная сборка агента сейчас windows-x64. На Windows `IcmpSendEcho` работает без прав администратора. На Linux сырой ICMP требует `CAP_NET_RAW` или `ping_group_range`.

- [x] Одна цель за запуск: имя или IP. Имя резолвит системный DNS. Ошибка имени не запускает пробы.
- [x] Непрерывный ICMP Echo с TTL от 1 до остановки. Таймаут пробы 5 с, флаг Don't Fragment, полезная нагрузка по умолчанию 64 байта, интервал 1 с. Следующая проба ждёт остаток интервала после RTT.
- [x] Максимум хопов задаётся пользователем. По умолчанию 30, верхняя граница около 64. В WinMTR README эта настройка обещана, в диалоге её нет: `MAX_HOPS` зашит как 30.
- [x] Пробы дальше цели не слать. Хвост обрывается, когда хоп совпал с адресом назначения или один и тот же адрес повторяется.
- [x] Счётчики хопа: отправлено, получено, потери в процентах, последняя, лучшая, средняя и худшая задержка в миллисекундах. Худшая считается отдельно. В WinMTR `SetWorst` пустой, и худшая обновляется только из ветки лучшей.
- [x] Код ICMP — отдельная причина, не общая строка «ошибка»: успех, TTL истёк в пути, сеть или хост недоступны, протокол или порт недоступны, пакет слишком большой, таймаут, плохой маршрут, parameter problem, source quench, ошибка сборки фрагментов, малый буфер, нет ресурсов, аппаратная ошибка. Молчащий хоп — «нет ответа», адрес пустой.
- [x] Обратный DNS для нового хопа и режим numeric. Пока имя не пришло, в строке IP.
- [x] Состояния Idle, Tracing и Stopping. Stop перестаёт слать новые пробы и дожидается уже ушедших. Отмена сессии агента останавливает трассировку так же, как отмена HTTP-запроса.
- [x] Живая таблица: номер, имя или IP, потери, sent, recv, best, avg, worst, last, последний код ICMP.
- [x] Карточка хопа: имя, IP, причина по коду ICMP и те же счётчики.
- [x] Копия в буфер и скачивание отчёта текстом и HTML-таблицей. Текст собирает страница из снимка. Агент файлы не пишет.
- [x] История целей и настройки инструмента (интервал, размер пакета, максимум хопов, numeric) в `localStorage`. Агент цели не помнит: сессии у него только в памяти.
- [x] Политика цели отличается от политики промежуточных хопов. Цель пользователя: частные и loopback-адреса только с `--allow-private`; metadata, link-local и multicast как цель запрещены всегда. Промежуточный хоп — наблюдение маршрута. Домашний шлюз и CGNAT `100.64.0.0/10` показываются всегда, иначе трассировка с обычного компьютера бесполезна.
- [x] IPv4 и IPv6. WinMTR умеет только IPv4.
- [x] Несколько трассировок сразу, с предельным числом параллельных сессий. Окна рабочего стола не делят одну ICMP-сессию.

**Проверено 2026-10-20:** страница `/en/path-trace/` на локальном dev-сервере против агента Linux (`--origin http://127.0.0.1:3312 --allow-private`). `127.0.0.1` и `::1` ответили Echo reply, счётчик отправленных рос до Stop, после остановки строка осталась. Windows `IcmpSendEcho` на этой машине не запускался. Путь по глобальному IPv6 не проверялся. Два окна `/en/desktop/` на том же агенте вели отдельные трассировки `127.0.0.1` и `::1`: остановка одного оставила второе в состоянии Tracing, третье окно при двух активных получило отказ busy, а после освобождения слота новая трассировка стартовала и не подменила оставшуюся. Публичная сборка агента по-прежнему только с `http.request`, пока не собран новый Windows-бинарник.

**Сверка с WinMTR 0.92 (2026-10-21):** по исходникам `WinMTRDialog.cpp`, `WinMTRNet.cpp`, `WinMTR.rc`. Добавлены пункт «Clear History» (кнопка «Очистить историю» у поля цели) и запуск по Enter в поле цели: в WinMTR кнопка Start стоит по умолчанию.
